# 03. Технологический стек и обоснование выбора

Каждый выбор сопровождается альтернативой и причиной отказа от неё. Формат:
**что → зачем → чем рискуем**.

## 3.1 Расчётное ядро

| Компонент | Выбор | Обоснование | Чем рискуем |
|---|---|---|---|
| Язык горячего пути | **C++20** | RAII для буферов интегралов, `constexpr` для шаблонных ядер по моменту `l`, предсказуемое время (нет GC-пауз в SCF-цикле) | Порог входа для контрибьюторов-химиков → компенсируется Python-референсом и Protocol-границей |
| Привязки к Python | **nanobind** | В 3–5 раз быстрее pybind11 на мелком ABI-трафике, меньше бинарный размер | Моложе pybind11 → при проблемах откат на pybind11 без изменения интерфейсов |
| Линейная алгебра | **BLAS/LAPACK** (OpenBLAS по умолчанию, MKL опционально) | Диагонализация и умножения — 60–80 % времени SCF; писать своё бессмысленно | Разброс результатов между BLAS на уровне 1e-14 → фиксируется в верификационных допусках |
| Параллелизм внутри узла | **OpenMP** (task-based) + **TBB** для динамических задач | Интегралы распараллеливаются по batch'ам оболочек; TBB даёт work-stealing для неравномерной загрузки | Ложное разделение кэша → батчи выравниваются по стоимости |
| Распределение между узлами | **MPI** (опционально, только для CCSD/крупных DFT) | Стандарт HPC; есть везде | Сложность отладки → MPI включается только там, где выигрыш измерен |
| GPU | **CUDA** (приоритет), **ROCm/HIP** (вторым) | Доля рынка; HIP-порт из CUDA-кода механический | Привязка к NVIDIA → абстракция `ComputeBackend` изолирует физику от устройства |
| Симд | компиляторные векторизации + явные ядра для `(ss\|ss)`, `(ps\|ss)` | Основная масса интегралов — короткие регулярные циклы | Разные наборы инструкций → runtime-dispatch по CPUID |
| Референсное ядро | **NumPy/Python** | Эталон корректности, доступный химику для чтения; с него начинаются все верификации | Медленно (в 50–200 раз) → никогда не используется в production-профиле |

**Почему не готовые пакеты целиком.** Psi4/PySCF — отличные движки, но лицензия
и архитектура (глобальное состояние, собственные схемы ввода) делают их
неудобным ядром продукта. Они подключаются как **внешние движки через адаптер**
(§42 ТЗ), а не как фундамент.

## 3.2 Платформа и backend

| Компонент | Выбор | Обоснование |
|---|---|---|
| Язык | **Python 3.11+** | Экосистема научных данных; типизация достаточна при `mypy --strict` |
| Доменные модели | **Pydantic v2** | Валидация и каноническая сериализация в ядре (Rust) — важно, потому что `CalculationSpec` хешируется в отпечаток |
| API | **FastAPI** | OpenAPI из аннотаций типов = контракт не разъезжается с кодом |
| SQL | **PostgreSQL 16** | JSONB для гибких метаданных + строгая схема для статусов; `SELECT … FOR UPDATE SKIP LOCKED` для очереди |
| Миграции | **Alembic** | Версионированная схема = обратимые деплои |
| Кэш/прогресс | **Redis** | TTL-ключи прогресса, распределённые блокировки, pub/sub для live-обновлений UI |
| Объектное хранилище | **S3-совместимое** (MinIO локально, S3/GCS в проде) | Один API для ноутбука и облака; content-addressed ключи |
| Очередь задач | **собственный scheduler поверх PostgreSQL** (не Celery) | Нужны специфичные семантики: приоритеты по проекту, вытесняющая отмена, рестарт с чекпоинта, HPC-планировщики как исполнители. Celery это не даёт, а абстракция «задача = строка в БД» проще и наблюдаемее |
| Наблюдаемость | **structlog + Prometheus + OpenTelemetry** | Структурные логи обязательны для разбора инцидентов расчётов |

## 3.3 Frontend

| Компонент | Выбор | Обоснование |
|---|---|---|
| Язык/фреймворк | **TypeScript + React 18 + Vite** | Компонентная модель подходит для «мастер + панель результатов»; строгая типизация ловит рассинхрон с API |
| 3D | **WebGL** через собственный рендерер (не готовый «молекулярный» компонент) | Нужны изоповерхности МО/ESP, инстансинг для 10⁴–10⁵ атомов, анимация нормальных мод; готовые компоненты упираются в потолок |
| WebGPU | целевой, через тот же абстрактный слой рендера | Пока покрытие браузеров неполное |
| Состояние | **TanStack Query** (серверное) + Zustand (локальное) | Расчёты — это серверное состояние с опросом; дублировать его в глобальном сторе — источник багов |
| i18n | ключи из каталога платформы, отдаваемые через `/api/v1/i18n/{locale}` | Один источник строк для UI, CLI и API-ошибок |
| Доступность | семантическая вёрстка, `aria-*`, фокус-ловушки в диалогах, контраст ≥ 4.5:1 | §35 ТЗ |

## 3.4 Инфраструктура

| Компонент | Выбор |
|---|---|
| Контейнеризация | Docker (multi-stage): образы `api`, `worker`, `worker-gpu` |
| Оркестрация | docker-compose (dev/single-node), Kubernetes (multi-node), нативные планировщики на HPC |
| HPC-интеграция | Slurm (приоритет), PBS, LSF — через единый `SchedulerAdapter` |
| CI/CD | GitHub Actions: lint → unit → integration → scientific → perf → security → build → release |
| Мониторинг | Prometheus + Grafana + Loki (логи) + Tempo (трейсинг) |

## 3.5 Что сознательно не берём

- **GraphQL** — REST с версионированием проще для научного API с тяжёлыми
  артефактами, а схемы запросов не нужны.
- **Микросервисы по каждому модулю ядра** — интегралы и SCF общаются гигабайтами
  матриц; разделять их сетью значит гарантированно упереться в сеть. Модули —
  это библиотеки, а не сервисы.
- **MongoDB как основное хранилище** — статусы и аудит требуют транзакций и
  внешних ключей.
- **Electron для десктоп-версии** — веб-версия покрывает сценарий; офлайн-режим
  решается локальным `quantumlab serve`.
