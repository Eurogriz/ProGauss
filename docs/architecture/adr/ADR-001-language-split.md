# ADR-001. C++20 для расчётного ядра, Python для платформы

**Статус:** принято · **Дата:** 2026-08-26

## Контекст
Горячий цикл (интегралы, SCF, XC-интегрирование) — плотные числовые циклы с
миллиардами операций. Интерфейсы, очередь, API и GUI — это оркестрация и
работа с состоянием. Требования к этим частям противоположны.

## Решение
Разделить систему по границе «плотные данные / оркестрация»:
C++20 (OpenMP, BLAS/LAPACK, опционально CUDA) для ядра, Python 3.11+ со
strict typing для всего остального. Связь — nanobind, реализующий
`Protocol`-интерфейсы из `quantumlab.engine.contracts`.

## Альтернативы
- **Всё на C++** — месяцы на то, что в Python решается библиотеками; GUI/API
  на C++ практически не поддерживаемы.
- **Всё на Python (+numba/cython)** — потолок производительности в 5–20 раз
  ниже C++ на интегральных рекурсиях; numba плохо работает с шаблонной
  специализацией по моменту `l`.
- **Julia** — интересный компромисс, но зрелость HPC-экосистемы (MPI, GPU,
  профилировщики) и доступность специалистов хуже.

## Последствия
- Нужен инструмент сборки нативной части (CMake + scikit-build-core) и CI с
  компилятором;
- Python-слой обязан быть строго типизирован, иначе граница превратится в
  источник ошибок (поэтому `mypy --strict` в CI);
- Любая новая возможность ядра появляется сначала в референсе (ADR-002).
