# 09. Верификация научной корректности и бенчмарки

Два разных вопроса, и смешивать их нельзя:

- **Верификация** — «считаем ли мы правильно?» (сравнение с эталонами);
- **Бенчмарк** — «считаем ли мы быстро?» (сравнение с собственной эталонной
  конфигурацией).

Верификация всегда предшествует бенчмарку: измерять скорость неверного расчёта
бессмысленно (§52 ТЗ).

---

## 9.1 Верификация (§26 ТЗ)

### Уровни

| Уровень | Что проверяется | Допуск | Где |
|---|---|---|---|
| L0. Математика | Рекурсии интегралов, квадратура, линейная алгебра | 1e-12 | unit-тесты |
| L1. Одноточечные энергии | RHF/DFT для эталонных молекул | 1e-8 Eh против референса; 1e-6 Eh против литературы | `verification/cases/energies` |
| L2. Градиенты | Аналитический градиент против численного | max\|Δ\| < 1e-6 Eh/Bohr | `verification/cases/gradients` |
| L3. Гессиан | Аналитический против численного по градиентам | max\|Δ\| < 1e-5 Eh/Bohr² | `verification/cases/hessian` |
| L4. Частоты | Эталонные наборы + отсутствие ложных мнимых | ±2 см⁻¹ к эталону | `verification/cases/frequencies` |
| L5. Геометрии | Оптимизированные структуры против эталонных | ±0.005 Å, ±0.5° | `verification/cases/geometries` |
| L6. Свойства | Диполи, заряды, мультиполи | dipole ±0.02 D | `verification/cases/properties` |
| L7. Симметрия | Инвариантность энергии к вращению/перенумерации атомов | 1e-10 Eh | `verification/cases/symmetry` |
| L8. Спин и заряд | ⟨S²⟩, сумма зарядов = заряду молекулы | ⟨S²⟩ ±1e-4 | `verification/cases/spin` |
| L9. Воспроизводимость | Повтор с тем же отпечатком даёт тот же результат | бит-в-бит на том же железе; 1e-12 на разных | `verification/cases/reproducibility` |
| L10. Backend-эквивалентность | optimized-cpu / CUDA против reference-cpu | 1e-8 Eh | CI на каждом backend'е |

### Эталоны

- **Внутренний референс** (`reference-cpu`) — главный арбитр для L1–L3: он
  написан «в лоб», его легко читать и проверять.
- **Публикуемые значения** — для L1, L4, L5, L6: геометрические эталоны
  (экспериментальные структуры воды, бензола, этилена), частоты и энергии из
  открытых наборов (NIST CCCBDB, GMTKN55 для DFT), с явной ссылкой на источник
  и допуском в каждом кейсе.
- **Внешние пакеты** — только как перекрёстная проверка, не как источник
  истины: у всех разные сетки, пороги и версии функционалов.

Формат кейса:

```yaml
id: benzene-pbe0-def2tzvp-opt
molecule: fixtures/benzene.xyz
spec:
  task: optimization
  method: { theory: dft, functional: pbe0, basis: def2-tzvp, dispersion: d3bj }
expect:
  energy_hartree: { value: -231.0000, tol: 1.0e-6, source: internal-reference }
  cc_bond_length_angstrom: { value: 1.394, tol: 0.005 }
  max_gradient_eh_bohr: { max: 4.5e-4 }
quality:
  no_imaginary_frequencies: true
  scf_converged: true
```

### Регрессия на каждый релиз (§26, §48 ТЗ)

Верификационный набор запускается в CI на каждом коммите (быстрая часть) и
полностью — перед релизом. Правила:

1. Провал верификации **блокирует релиз**, без исключений;
2. Изменение допуска требует ADR с объяснением, почему прежний допуск
   недостижим;
3. Новый метод/функционал/базис не получает статус `implemented` в реестре,
   пока не добавлены кейсы для него (§54 ТЗ).

### Что уже проверено сейчас

На текущем коммите проверяются доменные инварианты и логика платформы
(`tests/`, 84 теста): электронная структура и энергии — **нет**, потому что
ядро не реализовано. Поэтому все расчётные возможности имеют статус
`not_implemented`.

## 9.2 Бенчмарки (§27 ТЗ)

### Правило формулировок

> **Запрещено** писать «быстрее Gaussian» без воспроизводимых измерений на
> зафиксированной конфигурации. Бенчмарк сравнивает нас **с нашими же
> эталонными конфигурациями** и публикует абсолютные числа вместе с описанием
> железа и версий. Сравнение со сторонним пакетом допускается только при
> совпадении метода, базиса, сетки, порогов и версии — иначе это реклама, а не
> измерение.

### Измеряемые величины

| Метрика | Как измеряем |
|---|---|
| Wall time | от старта worker'а до записи результата |
| CPU time | сумма времени потоков |
| Пиковая память | `ru_maxrss` / cgroup-лимит |
| Загрузка GPU | `nvidia-smi`/NVML, средняя и p95 |
| Параллельное масштабирование | ускорение и эффективность на 1/2/4/…/N ядрах |
| Итерации SCF | из `ScfResult.iterations` |
| Время интегралов / диагонализации / XC | спаны OpenTelemetry |
| Коммуникационные издержки | время MPI-обменов отдельно от вычислений |
| Доля отброшенных интегралов | метрика скрининга |

### Наборы задач

| Набор | Состав | Зачем |
|---|---|---|
| `small` | H₂O, NH₃, CH₄ (≤ 5 атомов) | накладные расходы, старт SCF |
| `medium` | бензол, кофеин (6–25 атомов) | основной рабочий диапазон |
| `large` | пептиды, фуллерены (50–500 атомов) | скрининг, direct SCF, память |
| `gpu` | те же молекулы на CUDA-backend | проверка ускорения |
| `multi-node` | 200+ атомов, 2–8 узлов | MPI-масштабирование |

### Эталонные конфигурации

Для каждого набора фиксируется **reference configuration**: конкретное железо,
версии ПО и BLAS, настройки окружения, и измеренные значения. Хранится в
`benchmarks/reference/*.json`. Результат прогона сравнивается с эталоном:

```json
{
  "suite": "medium", "case": "benzene-pbe0-def2tzvp-sp",
  "hardware": "2x EPYC 9454, 96 cores, OpenBLAS 0.3.27",
  "versions": { "quantumlab": "0.4.0", "engine": "0.4.0" },
  "metrics": { "wall_s": 142.3, "cpu_s": 5210.7, "peak_rss_mb": 18432,
               "scf_iterations": 14, "integral_time_s": 98.1 },
  "tolerance": { "wall_s": "+10%" }
}
```

Деградация больше допуска — **красный CI**, а не «шум».

### Методика прогона

1. Фиксированная частота CPU (без turbo-разгона, если возможно), привязка
   потоков к ядрам, `numactl` для NUMA;
2. 5 прогонов, в отчёт идут медиана и разброс;
3. Прогрев: первый прогон исключается (кэши файловой системы, JIT);
4. Изоляция: только одно задание на узле;
5. Все параметры расчёта — из отпечатка, чтобы прогон был воспроизводим;
6. Публикуются и сырые данные (CSV/Parquet), и скрипт запуска.

### Профилирование перед оптимизацией

Порядок обязателен (§51, §52 ТЗ):

```text
Correctness → Verification → Profiling → Optimization → Benchmarking
```

Профилировщик: `perf` + собственная инструментация этапов. Любая оптимизация
сопровождается записью в ADR: почему выбрана, какова сложность, где
масштабируется плохо, какое ускорение ожидается, как это проверить.

### Что публикуем

- абсолютные числа (секунды, ГБ, итерации), а не только относительные;
- полное описание окружения и отпечаток конфигурации;
- известные ограничения («MPI-режим недетерминирован на уровне 1e-13»);
- негативные результаты (где ускорения нет) — они защищают от повторения
  тупиковых веток.
