# 10. План реализации, MVP и production roadmap

## 10.1 Принцип этапа

Каждый этап — **вертикальный срез**, а не горизонтальный слой (§51 ТЗ):

```text
1. архитектура → 2. интерфейсы → 3. минимальный рабочий срез
→ 4. тесты → 5. научная верификация → 6. бенчмарк
→ 7. профилирование → 8. устранение bottleneck → 9. следующий уровень
```

Критерий завершения этапа: пользователь может выполнить сквозной сценарий, а
не «модуль написан».

## Этап 2 — Core quantum engine  ← **выполняется сейчас (частично)**

Цель: **научно достоверный** расчёт энергии и градиента.

| Задача | Статус |
|---|---|
| `basis-library`: схема базисов, 16 наборов из Basis Set Exchange с записью происхождения | ✅ |
| Пользовательские базисы (своя схема, загрузка из файла) | ⏳ |
| `integral-engine`: референс (NumPy) → S, T, V, ERI, диполь | ✅ сверено до 1e-14 |
| `scf-engine`: RHF, DIIS, гашение, сдвиг уровней, `strategies_used` | ✅ сверено с PySCF до 1e-6 Eh |
| Устойчивость SCF: EDIIS, адаптивный выбор, анализ устойчивости | ⏳ |
| Аналитические градиенты RHF по координатам ядер | ✅ сверено с конечными разностями |
| Оптимизация геометрии в декартовых координатах (BFGS + trust radius) | ✅ |
| Избыточные внутренние координаты, ограничения, связи | ⏳ |
| `ReferenceEngine` (протокол `QuantumEngine`): `single_point` с проверками качества | ✅ |
| Доведение расчёта до пользователя: CLI `run --task energy` сохраняет результат | ✅ |
| Сферическая схема базисов (5 d- и 7 f-функций) | ⏳ сейчас только декартова |
| UHF/ROHF | ⏳ |
| DFT-фундамент: квадратура, PBE, PBE0 | ⏳ |
| `reference-cpu` backend, зарегистрированный в реестре как `implemented` | ✅ |

**Верификация:** L0–L3, L7 (энергии, градиенты, симметрия).
**Бенчмарк:** `small` + `medium`, baseline для будущих сравнений.
**Выход:** `quantumlab run water.xyz --task energy --profile standard` считает
настоящую энергию; статус `method:dft` становится `implemented`.

**Что уже достигнуто.** `quantumlab run water.xyz --task energy --method hf
--basis sto-3g` выполняет настоящий RHF-расчёт, а `--task optimize` —
оптимизацию геометрии с сохранением итоговой структуры. Профиль `standard` пока
приводит к DFT и потому честно отказывается — автоподбор не будет обещать того,
чего в ядре нет.

**Проверки, на которых это держится.** Аналитический градиент сверяется с
конечными разностями той же энергии (вода/STO-3G: 5.7e-08 э/бор), оптимизатор —
с независимым поиском минимума бисекцией (H₂: 0.7124 против 0.7122 Å).

**Что сознательно не достигнуто.** Статус `method:hf` — `partial`, а не
`implemented`: реализован только RHF и только `single_point`. Десять базисов с
d/f-функциями тоже `partial`: мы считаем в декартовой схеме, тогда как они
опубликованы в сферической, и это больший базис (энергия ниже табличной примерно
на 1e-4 Eh). Оба ограничения видны и в реестре, и в предупреждениях результата.

Риски: корректность XC-ядер и производных интегралов — самые частые источники
тихих ошибок → обязателен тест «аналитический градиент = численный» на каждой
молекуле верификационного набора.

## Этап 3 — Molecular workflows

- оптимизация геометрии (редундантные внутренние координаты, RFO, trust radius);
- частоты, ИК/КР, ZPE, термодинамика;
- свойства: диполь, заряды, орбитали, плотности, ESP;
- молекулярный редактор (2D/3D), импорт XYZ/MOL/SDF/PDB, SMILES/InChI;
- Web UI: мастер, очередь, страница результата;
- Job Manager на PostgreSQL + scheduler `local`;
- REST API + SSE-прогресс.

**Верификация:** L4, L5, L6 (частоты, геометрии, свойства).
**Выход:** полный MVP-сценарий (§53 ТЗ) — от рисования молекулы до HOMO/LUMO.

---

## Этап 4 — Performance

- `optimized-cpu` backend: C++20, OpenMP, BLAS/LAPACK, SIMD;
- скрининг Шварца, direct SCF, кэширование интегралов;
- density fitting (RI-J/RI-K), Cholesky;
- UHF/ROHF, MP2, SCS-MP2;
- GPU-backend (CUDA) для плотных блоков;
- смешанная точность там, где доказуемо безопасно;
- система бенчмарков с эталонными конфигурациями и порогами деградации.

**Верификация:** L10 — эквивалентность backend'ов референсу (1e-8 Eh).
**Бенчмарк:** масштабирование по ядрам и GPU, `large`-набор.
**Правило:** каждая оптимизация — с записью в ADR (алгоритм, сложность, где
масштабируется плохо, ожидаемое ускорение, способ проверки).

---

## Этап 5 — HPC

- MPI-распределение для DFT/MP2/CCSD;
- адаптеры Slurm / PBS / LSF / Kubernetes;
- распределённые worker'ы, многoузловые задания;
- workflow-пайплайны (§37 ТЗ) и пакетный режим (§38 ТЗ);
- рестарт на другом узле.

**Бенчмарк:** `multi-node`, коммуникационные издержки отдельной метрикой.

---

## Этап 6 — Production

- RBAC, изоляция проектов, secrets management, TLS, аудит;
- sandboxing пользовательских заданий, лимиты ресурсов;
- мониторинг, алерты, дашборды, SLO;
- бекапы БД и object storage, восстановление по расписанию;
- HA: несколько реплик API, активный планировщик с `SKIP LOCKED`;
- отчетность и экспорт (§39 ТЗ), версионирование релизов, deprecation policy.

## 10.3 Definition of Done (§49 ТЗ)

| Требование | Как проверяем |
|---|---|
| GUI работает | e2e-тест сценария MVP (Playwright) |
| Русский интерфейс полностью функционирует | тест паритета + e2e на `ru` |
| Английская локализация присутствует | тест паритета ключей |
| Ядро проходит verification | верификационный набор L1–L10 в CI |
| Есть benchmark suite | `benchmarks/` с эталонами и порогами |
| Есть restart | тест «убить worker → продолжить с чекпоинта» |
| Есть logging | структурные логи с `job_id` в каждом событии |
| Есть monitoring | Prometheus-метрики и health-пробы |
| Есть CLI / Python API / REST API | смоук-тесты каждого интерфейса |
| Есть Docker deployment | сборка образов и compose-поднятие в CI |
| Есть документация | `docs/` на русском, ссылки не битые |
| Есть автотесты и regression suite | покрытие ≥ 80 % по платформенному слою |

## 10.4 Roadmap производства (после MVP)

1. **Расширение методов**: CCSD, CCSD(T), TD-DFT, мультиреференсные методы —
   каждый со своим верификационным набором до публикации статуса.
2. **Расширение форматов**: CIF, MOL2, crYStal-структуры, периодические системы.
3. **Коллаборация**: общие проекты, комментарии к расчётам, версионирование
   структур.
4. **Данные**: поиск по базе результатов, агрегированные наборы для ML.
5. **Экосистема**: публичный реестр плагинов (методы, форматы, планировщики).
6. **Производительность**: WebGPU-визуализация, стриминг крупных систем,
   кэширование интегралов между заданиями.

## 10.5 Компромиссы, которые мы принимаем осознанно

| Компромисс | Цена | Почему приемлемо |
|---|---|---|
| Референсное ядро навсегда в коде | +поддержка двух реализаций | Это единственный надёжный арбитр корректности |
| Собственный scheduler вместо Celery | больше своего кода | Нужны приоритеты по проектам, рестарт с чекпоинта и HPC-планировщики как исполнители |
| Монорепозиторий | большие CI-прогоны | Контракты меняются сразу во всех слоях; версионный ад исключён |
| Плотные массивы в референсе | O(N⁴) память | Референс не для крупных систем — для проверки |
| Плагинная система с самого начала | более сложная архитектура | Иначе внешние движки и новые методы потребуют переписывания ядра |
