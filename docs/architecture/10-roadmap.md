# 10. План реализации, MVP и production roadmap

## 10.1 Принцип этапа

Каждый этап — **вертикальный срез**, а не горизонтальный слой (§51 ТЗ):

```text
1. архитектура → 2. интерфейсы → 3. минимальный рабочий срез
→ 4. тесты → 5. научная верификация → 6. бенчмарк
→ 7. профилирование → 8. устранение bottleneck → 9. следующий уровень
```

Критерий завершения этапа: пользователь может выполнить сквозной сценарий, а
не «модуль написан».

**Верификация:** L0–L3, L7 (энергии, градиенты, симметрия).
**Бенчмарк:** `small` + `medium`, baseline для будущих сравнений.
**Выход:** `quantumlab run water.xyz --task energy --profile standard` считает
настоящую энергию; статус `method:dft` становится `implemented`.

**Что уже достигнуто.** `quantumlab run water.xyz --task energy --method hf
--basis sto-3g` выполняет настоящий RHF-расчёт, а `--task optimize` —
оптимизацию геометрии с сохранением итоговой структуры.

Автоподбор сверяется с реестром возможностей по **всему обещанию профиля** —
функционалу и дисперсионной поправке — и снимает ровно то, чего в ядре нет.
Текущее разрешение четырёх профилей на воде в одноточечном расчёте:

| Профиль | Обещает | Выдаёт сейчас | Что снято |
|---|---|---|---|
| Скрининг | PBE/def2-SVP + D3(BJ) | `dft/pbe/def2-svp/d3bj` | — |
| Стандарт | PBE0/def2-SVP + D3(BJ) | `dft/pbe0/def2-svp/d3bj` | — |
| Высокая точность | PBE0-D3(BJ)/def2-TZVP | `dft/pbe0/def2-tzvp/d3bj` | — |
| Исследовательский | ωB97X-D/def2-TZVP | `dft/pbe0/def2-tzvp/none` | функционал (ωB97X-D → pbe0) |

Правило «недоступная часть обещания снимается отдельным видимым решением»
осталось и работает: дисперсионная поправка — аддитивное слагаемое, а не
уровень теории, поэтому снятая поправка не понижает профиль, а записывается
решением («Дисперсионная поправка, которую предполагает этот профиль, ещё не
реализована — расчёт пойдёт без неё»). Неразличение этого с откатом профиля в
HF было дефектом: прежний «строгий» вариант откатывал все четыре профиля
в HF целиком, и свёрённые с LibXC/PySCF функционалы были недостижимы через
основной сценарий ТЗ — пользователь получал менее точный метод при полностью
исправном ядре. В HF план уходит только тогда, когда реализованного
функционала нет ни одного.

Учитывать нужно именно всё обещание, а не только функционал: проверка только
по функционалу уже давала сбой — когда появился PBE, профиль «Скрининг» начал
бы обещать PBE-D3(BJ), и расчёт выполнился бы без дисперсионной поправки,
выдав другое число под тем же описанием (§54 ТЗ). Разница между «снять с
объяснением» и «промыть» — в том, что первое видно в плане, а второе нет.
Раньше рекомендатель выдавал DFT-функционал, которого в ядре нет, — такой
расчёт падал сразу после нажатия «Рассчитать». Дефект вскрылся, когда план
начали исполнять через REST API: до этого `run --profile standard` просто
отказывался, и нерабочий план никто не выполнял.

**Верификация и бенчмарки (§26, §27).** Каталоги `verification/` и
`benchmarks/` заполнены: 10 декларативных кейсов на уровнях L1/L2/L5/L7/L9 и
набор `small` с эталоном и допуском деградации. Уровней L3/L4/L6/L8/L10 нет —
соответствующие расчёты не реализованы, и эталоны для них не выдумываются.

**Дефект SCF, найденный на открытой оболочке.** Сдвиг уровней включался и не
выключался никогда. Сдвинутый фокиан ``F + λP_вирт`` имеет другую стационарную
точку, поэтому при постоянно включённом сдвиге условие стационарности исходной
задачи не выполняется в принципе: на радикале CH/STO-3G энергия сходилась до
1e-14, а невязка застревала на 1e-7 и расчёт не проходил по критерию вообще.
На замкнутой оболочке дефект не проявлялся — там DIIS успевает сойтись до
включения сдвига. Теперь сдвиг выключается при невязке ниже `1e-2`; порог
выбран измерением на CH/STO-3G (1e-2 → 44 итерации, 1e-3 → 77, 1e-4 → 133,
1e-5 → не сходится за 300).

**Профилирование и ускорение (§52: после корректности и верификации).**
Профиль градиента показал, что узкое место — скалярные циклы по примитивным
квартетам, а не арифметика. Кеш функции Бойса и векторизация блока производной
дали 6.56 с → 1.15 с на воде/STO-3G; оба шага сверены со скалярной реализацией
и с конечными разностями. Тот же приём применён к сборке ERI для энергии
(вода/cc-pVDZ: 112 с → 10.5 с). Числа — в README.

**Проверки, на которых это держится.** Аналитический градиент сверяется с
конечными разностями той же энергии (вода/STO-3G: 5.7e-08 э/бор), оптимизатор —
с независимым поиском минимума бисекцией (H₂: 0.7124 против 0.7122 Å).

**Что сознательно не достигнуто.** Статус `method:hf` — `partial`, а не
`implemented`: реализован только RHF и только `single_point`. Десять базисов с
d/f-функциями тоже `partial`: мы считаем в декартовой схеме, тогда как они
опубликованы в сферической, и это больший базис (энергия ниже табличной примерно
на 1e-4 Eh). Оба ограничения видны и в реестре, и в предупреждениях результата.

Риски: корректность XC-ядер и производных интегралов — самые частые источники
тихих ошибок → обязателен тест «аналитический градиент = численный» на каждой
молекуле верификационного набора.

## Этап 3 — Molecular workflows

- оптимизация геометрии (редундантные внутренние координаты, RFO, trust radius);
- частоты, ИК/КР, ZPE, термодинамика;
- свойства: диполь, заряды, орбитали, плотности, ESP;
- молекулярный редактор (2D/3D), импорт XYZ/MOL/SDF/PDB, SMILES/InChI;
- Web UI: мастер, очередь, страница результата;
- Job Manager на PostgreSQL + scheduler `local`;
- REST API + SSE-прогресс.

**Что уже сделано.** REST API поднят как вертикальный срез: 15 операций из 26
реализованы (здоровье, возможности, i18n, проекты, структуры, план, задания,
результат), остальные 11 отвечают `501` с кодом `api.not_implemented` — путь
объявлен контрактом, и прятать его за `404` нельзя. Очередь исполняет отдельный
воркер: `POST /jobs` возвращает `202`, потому что многосекундный расчёт внутри
HTTP-запроса не переживёт ни таймаут, ни перезапуск процесса (§14 ТЗ).

SSE-прогресса нет: он требует настоящего длинного расчёта с промежуточными
итерациями, а не эмуляции потока событий.

**Верификация:** L4, L5, L6 (частоты, геометрии, свойства).
**Выход:** полный MVP-сценарий (§53 ТЗ) — от рисования молекулы до HOMO/LUMO.

## Этап 4 — Performance

- `optimized-cpu` backend: C++20, OpenMP, BLAS/LAPACK, SIMD;
- скрининг Шварца, direct SCF, кэширование интегралов;
- density fitting (RI-J/RI-K), Cholesky;
- UHF/ROHF, MP2, SCS-MP2;
- GPU-backend (CUDA) для плотных блоков;
- смешанная точность там, где доказуемо безопасно;
- система бенчмарков с эталонными конфигурациями и порогами деградации.

**Верификация:** L10 — эквивалентность backend'ов референсу (1e-8 Eh).
**Бенчмарк:** масштабирование по ядрам и GPU, `large`-набор.
**Правило:** каждая оптимизация — с записью в ADR (алгоритм, сложность, где
масштабируется плохо, ожидаемое ускорение, способ проверки).

## 10.2 MVP (§53 ТЗ) — критерии приёмки

## 10.3 Definition of Done (§49 ТЗ)

## 10.4 Roadmap производства (после MVP)

1. **Расширение методов**: CCSD, CCSD(T), TD-DFT, мультиреференсные методы —
   каждый со своим верификационным набором до публикации статуса.
2. **Расширение форматов**: CIF, MOL2, crYStal-структуры, периодические системы.
3. **Коллаборация**: общие проекты, комментарии к расчётам, версионирование
   структур.
4. **Данные**: поиск по базе результатов, агрегированные наборы для ML.
5. **Экосистема**: публичный реестр плагинов (методы, форматы, планировщики).
6. **Производительность**: WebGPU-визуализация, стриминг крупных систем,
   кэширование интегралов между заданиями.

## 10.5 Компромиссы, которые мы принимаем осознанно

| Компромисс | Цена | Почему приемлемо |
|---|---|---|
| Референсное ядро навсегда в коде | +поддержка двух реализаций | Это единственный надёжный арбитр корректности |
| Собственный scheduler вместо Celery | больше своего кода | Нужны приоритеты по проектам, рестарт с чекпоинта и HPC-планировщики как исполнители |
| Монорепозиторий | большие CI-прогоны | Контракты меняются сразу во всех слоях; версионный ад исключён |
| Плотные массивы в референсе | O(N⁴) память | Референс не для крупных систем — для проверки |
| Плагинная система с самого начала | более сложная архитектура | Иначе внешние движки и новые методы потребуют переписывания ядра |
