# Верификационный набор

Отвечает на вопрос **«считаем ли мы правильно?»** — в отличие от `benchmarks/`,
которые отвечают на вопрос «считаем ли мы быстро?». Верификация всегда
предшествует бенчмарку: измерять скорость неверного расчёта бессмысленно (§52 ТЗ).

Проект — `docs/architecture/09-verification-and-benchmark.md`.

## Запуск

```bash
python verification/run_verification.py              # весь набор (~2.5 мин)
python verification/run_verification.py --fast       # без дорогих кейсов (~8 с)
python verification/run_verification.py --level L1   # один уровень
python verification/run_verification.py --list       # перечень
make verify                                          # то же, что полный прогон
```

Быстрая часть выполняется и в общем прогоне тестов
(`tests/test_verification_suite.py`); дорогие кейсы помечены `slow`.

## Что покрыто сейчас

| Уровень | Кейсов | Что проверяется | Фактический запас |
|---|---|---|---|
| L1. Одноточечные энергии | 4 | RHF, 4 базиса, воды и H₂ | допуск 1e-8 Eh, фактически ≤ 3e-11 |
| L2. Градиенты | 2 | аналитический против центральной разности | допуск 1e-6 э/бор, фактически 5.7e-08 |
| L5. Геометрии | 1 | оптимизация воды: длины связей и валентный угол | ±0.005 Å / ±0.5°, фактически 1.6e-09 Å |
| L7. Симметрия | 2 | инвариантность к вращению и перенумерации атомов | допуск 1e-10 Eh, фактически ≤ 1e-13 |
| L9. Воспроизводимость | 1 | повтор даёт тот же отпечаток и ту же энергию | побитово (0.0) |

## Чего в наборе нет — и почему

Уровни **L3 (гессиан), L4 (частоты), L6 (мультипольные свойства), L8 (спин)**
и **L10 (эквивалентность backend'ов)** не имеют ни одного кейса, потому что
соответствующие расчёты не реализованы. Добавлять для них «ожидаемые» значения
означало бы выдумывать эталоны для кода, которого нет (§54 ТЗ). Тест
`test_known_levels_are_covered` фиксирует состав набора, поэтому новый
реализованный расчёт без кейса не пройдёт незамеченным.

## Источники эталонов

Все текущие эталоны — `internal-reference`: значения, полученные самим
референсным ядром при жёстких порогах. Это отвечает роли `reference-cpu` как
главного арбитра для L1–L3 (код написан «в лоб», его легко читать).

**Сравнение с публикуемыми значениями и с внешними пакетами в этот набор не
входит.** Перекрёстная сверка с PySCF живёт в `tests/test_crosscheck_pyscf.py`
(маркер `scientific`): внешние пакеты — только перекрёстная проверка, не
источник истины, потому что у них свои сетки, пороги и версии функционалов.

## Правила

1. Провал верификации **блокирует релиз**, без исключений.
2. Изменение допуска требует ADR с объяснением, почему прежний недостижим.
3. Новый метод, функционал или базис не получает статус `implemented`
   в реестре возможностей, пока для него нет кейса.
4. Неизвестное поле в YAML — ошибка, а не пропуск: молча проигнорированная
   проверка создаёт ложное впечатление покрытия.
