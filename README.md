# QuantumLab

**Профессиональная квантовая химия, которой можно пользоваться без изучения
языка input-файлов.**

Сложность находится внутри системы, а не на плечах пользователя: молекула →
тип расчёта → уровень точности → «Рассчитать». При этом эксперт никогда не
упирается в потолок интерфейса — полный контроль доступен через расширенные
настройки, CLI и API.

> **Статус проекта: Этап 2 (Compute core) — частично.** Реализован контрактный
> слой платформы (Этап 1) и **референсное расчётное ядро**: базисные наборы,
> интегралы по McMurchie–Davidson, RHF с DIIS, аналитические градиенты и
> оптимизация геометрии. Всё доступно из CLI как настоящий расчёт.
> Энергии сверены с PySCF как независимым оракулом — расхождение ≤ 1e-6 Eh на
> пяти базисах; аналитический градиент сверен с конечными разностями до 1e-6 э/бор.
> Умеет: **энергию RHF в точке, UHF и ROHF для открытой оболочки (с
> аналитическим градиентом), DFT (SVWN, PBE, PBE0, BLYP, B3LYP), дисперсионную
> поправку DFT-D3 (BJ и zero-затухание, аналитический градиент), колебательные
> частоты и оптимизацию геометрии** (декартовы координаты).
> meta-GGA (TPSSh, M06-2X), ωB97X(-D), UKS, дисперсионная поправка D4,
> MP2/CC, Web UI и планировщики **не реализованы** — система сообщает об этом
> прямо, а не имитирует расчёт.
> Проверить: `quantumlab capabilities`.

## Быстрый старт

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

quantumlab version
quantumlab molecule inspect tests/fixtures/water.xyz
quantumlab plan tests/fixtures/water.xyz --task optimize --profile high-accuracy

# Настоящий расчёт: энергия RHF в одной точке
quantumlab run tests/fixtures/water.xyz --task energy --method hf --basis sto-3g
quantumlab job list

# Оптимизация геометрии (декартовы координаты, BFGS)
quantumlab run tests/fixtures/water.xyz --task optimize --method hf --basis sto-3g

# Не реализовано — и система говорит об этом прямо:
quantumlab run tests/fixtures/water.xyz --task freq --method hf --basis sto-3g
```

Русский интерфейс — по умолчанию, английский — `--lang en`.

Реальный запуск даёт энергию, орбитали, диполь и проверки качества:

```
Запускаю Одноточечный расчёт методом hf в базисе sto-3g…
  SCF сошёлся за 8 итераций
  Энергия: -74.9630296563 э · ЗМО: -0.391243 э · НСМО: 0.605165 э · Диполь: 1.7253 Д
  Результат сохранён: ~/.quantumlab/results/<id>.json
```

### REST API

Контракт — `api/openapi/v1.yaml`. Сервер поднимается фабрикой, поэтому тесты
работают на временном каталоге и не трогают `data/`:

```bash
uvicorn --factory quantumlab.server:create_app --host 0.0.0.0 --port 8000
```

Реализовано 15 операций из 26: здоровье и готовность, срез возможностей,
каталог строк интерфейса, проекты и структуры, подбор параметров, приём
задания и выдача результата. Остальные 11 отвечают `501`.

`POST /jobs` только ставит расчёт в очередь и возвращает `202`: выполнять
многосекундный расчёт внутри HTTP-запроса нельзя ни по таймаутам, ни по
восстановлению после сбоя (§14 ТЗ). Выполняет очередь воркер:

```python
from quantumlab.server.worker import run_pending_jobs

run_pending_jobs(services.jobs, services.catalog)
```

Ответы приводятся к `camelCase` на границе HTTP; доменная модель остаётся в
`snake_case`, потому что от неё зависят отпечаток расчёта и JSON артефактов.

### Верификация и бенчмарки

Два разных вопроса, и они разведены по разным каталогам (§26, §27 ТЗ):

```bash
make verify   # «считаем ли мы правильно?» — 15 кейсов, ~25 с
make bench    # «считаем ли мы быстро?»     — набор small, ~20 с
```

Верификация (`verification/cases/*.yaml`) покрывает L1 энергии, L2 градиенты,
L5 геометрии, L7 симметрию и L9 воспроизводимость. Уровней L3/L4/L6/L8/L10
в наборе **нет**. Для L6 (мультипольные свойства), L8 (спин-орбиталь) и L10
(второй backend) причина — отсутствие кода: выдумывать эталоны для него
нельзя (§54 ТЗ). Для L3 (гессиан) и L4 (частоты) причина другая и менее
удобная: частоты реализованы и сверены с PySCF тестами, но тип ожидания
«частоты» в верификационном движке не заведён, поэтому отдельного кейса нет.
Состав набора зафиксирован тестом, поэтому новый реализованный расчёт без
кейса не пройдёт незамеченным.

Бенчмарки (`benchmarks/`) публикуют абсолютные числа и сравнивают их
с эталоном в `benchmarks/reference/small.json`; деградация wall time больше
+10% даёт ненулевой код возврата. **Сравнений с Gaussian или PySCF нет** —
по §27 ТЗ они допустимы только при совпадении метода, базиса, сетки, порогов
и версии, чего здесь не обеспечить. Заблокированных кейсов сейчас нет:
бензол/6-31G был заблокирован из-за 245 с на сборку ERI и разблокирован после
пакетной сборки квартетов (12.2 с на интегралы, 28.2 с на весь расчёт).

### Куда ушло время интегралов (измерено, не оценено)

Профилирование воды/STO-3G показало, что стоимость определяется не арифметикой,
а накладными расходами: 1.34 млн вызовов функции Бойса и 422 тыс. проходов
скалярного цикла по примитивным квартетам при 7 базисных функциях.

| Шаг | Градиент воды/STO-3G |
| --- | --- |
| Было: скалярный цикл по квартетам | 6.56 с |
| + кеш функции Бойса (`x = αR²` зависит только от квартета) | 4.50 с |
| + векторизация блока производной по примитивам | **1.15 с** |

Каждый шаг проверен: кеш функции Бойса — совпадением со скалярной функцией на
обеих ветвях (ряд и `erf`), векторизация — поблочным сравнением со скалярной
реализацией на `s`- и `p`-оболочках (расхождение ≤ 2e-15), конечными
разностями энергии (5.7e-08 э/бор) и сверкой с PySCF (19 тестов).

Тот же приём применён к сборке ERI для энергии:

| Расчёт | Было | Стало |
| --- | --- | --- |
| вода/cc-pVDZ, одна точка | 112 с | **10.5 с** |
| вода/6-31G, одна точка | 4.07 с | **1.76 с** |
| оптимизация воды/STO-3G | 16.19 с | **12.13 с** |

Третий шаг того же ряда — **пакетная сборка квартетов**. Стоимость определялась
числом обращений к NumPy, а не арифметикой: 83 тыс. вызовов `_hermite_1d` на
3081 квартет, ~600 мкс на квартет при 25 базисных функциях. Квартеты одного
класса (одинаковые угловые моменты и длины сжатий) теперь считаются одним
массивом, поэтому тот же объём арифметики выполняется за один проход:

| Расчёт | Было | Стало |
| --- | --- | --- |
| бензол/6-31G, сборка ERI (66 функций) | 242.9 с | **11.6 с** (20.9×) |
| вода/cc-pVDZ, сборка ERI | 4.98 с | **1.03 с** (4.8×) |
| оптимизация воды/STO-3G (весь расчёт) | 12.13 с | **2.84 с** (4.3×) |
| градиент воды/STO-3G (весь расчёт) | 1.41 с | **0.51 с** (2.8×) |

Числа — медианы прогонов `benchmarks/` на том же железе; эталон
`benchmarks/reference/small.json` перезаписан, прежние значения остались в
истории git. Совпадение с поквартиетной сборкой проверяется по всему тензору
(`test_batched_eri_matches_quartetwise_assembly`, ≤ 1e-12), а независимость
результата от размера пачки — отдельным тестом.

Попутно нашлась вторая причина медлительности: этап `integrals` отчитывался
о 0.012 с, тогда как сборка ERI (~1 с) попадала в этап `scf`, а проверка
разложения энергии строила тензор ERI **второй раз за расчёт**. Теперь
интегралы собираются один раз и передаются в SCF и в проверки; тест
`test_eri_build_is_not_repeated_by_quality_checks` ловит возврат к прежнему.

### Бенчмарк измерял двойную работу

Профилирование бензола/6-31G вскрыло дефект не в движке, а в самом стенде:
wall-время кейса было 27.7 с, тогда как сумма его же этапов — 14.0 с, и
запуск интерпретатора с импортом пакета стоит 0.27 с. Недостающие 13.7 с —
это второй полноценный расчёт: рабочий процесс бенчмарка сначала запускал
`run_rhf`, чтобы снять число итераций SCF, а потом `ReferenceEngine.run`,
который считает то же самое заново. На бензоле 12.4 с сборки ERI выполнялись
дважды.

Число итераций теперь берётся из результата движка (`result.scf_iterations`);
отдельный `run_rhf` остался только в ветви `measure_gradient`, где он и есть
измеряемая работа. Заодно выяснилось, что прежние 13 итераций относились к
*другому* расчёту: у «голого» `run_rhf` пороги сходимости 1e-9/1e-7, у движка
из спецификации — 1e-8/1e-6, поэтому итераций 12. Энергия совпадает до
−75.983970346119 э в обоих случаях.

| Кейс (`--suite medium`) | Было в отчёте | Стало |
| --- | --- | --- |
| бензол/6-31G, одна точка | 28.17 с | **14.98 с** (интегралы 12.72, SCF 0.89, свойства 0.91) |
| вода/cc-pVDZ, одна точка | 2.64 с | **1.59 с** (интегралы 1.17) |

Вне этапов теперь остаётся ~0.3–0.5 с — это интерпретатор и импорт, а не
невидимая работа движка.

**Допуск бенчмарка получил абсолютный порог.** Относительные 10 % на кейсе
в 0.3 с — это 30 мс, меньше шума стенда: повторный прогон *того же кода* дал
систематическое смещение +0.026…+0.049 с по всем пяти кейсам `small`, и
стенд рапортовал «ДЕГРАДАЦИЯ» на неизменённом коде. Теперь допуск равен
`max(10 %, 0.1 с)` для времени (память и итерации судятся по-прежнему
относительно), и в отчёте видно, какой из двух порогов сработал. Замедление
вдвое порог по-прежнему ловит. Отчёт и код выхода судят о деградации по одному
и тому же обходу метрик: раньше `degraded` смотрел только на `wall_s`, поэтому
изменившееся число итераций печатало «ДЕГРАДАЦИЯ» при нулевом коде выхода.

### Известные ограничения расчётного ядра

* **Оптимизация — только в декартовых координатах.** Избыточные внутренние
  координаты (дефолт спецификации) не реализованы: запрос на них отклоняется,
  а автоподбор выбирает декартовы **с видимым обоснованием**. У декартовых
  координат есть шесть нулевых мод (поступательные и вращательные), из-за чего
  приближение гессиана хуже и сходимость ближе к линейной: воде/STO-3G
  потребовалось 9 шагов. Центр масс не закреплён, поэтому молекула в процессе
  оптимизации свободно смещается — на энергию это не влияет.
* **Только декартова схема.** Для базисов с d/f-функциями (cc-pV\*, aug-cc-pV\*,
  def2-\*) мы используем 6 декартовых d-функций вместо 5 сферических. Это
  корректный, но **больший** базис: энергии отличаются от общепринятых значений
  на ~1e-4 Eh. Данные помечены полем `angular_scheme_published`, статус в
  реестре — `partial`, а не `implemented`.
* **DFT доступен только для замкнутой оболочки.** UKS (спиново-поляризованный
  DFT) не реализован, поэтому `--spin uhf --method dft` (и `rohf`) отклоняется
  штатной ошибкой `engine.combination_unavailable`, а не падает внутри RKS-пути.
  Нечётное число электронов при `--spin rhf` отклоняется, а не молчаливым
  неверным результатом. ROHF, в отличие от DFT, считает оптимизацию и частоты —
  через аналитический градиент с фокиан-зависимыми весами релаксации.
* **Константа перевода Å в боры — CODATA-1998** (1.8897259885789), тогда как
  PySCF и текущий CODATA-2018 используют 1.8897261246. Разница 7.2e-8 отн.
  даёт 6.6e-7 э в ядерном отталкивании воды и объясняет расхождение энергий
  с PySCF на уровне 1e-8 э при интегралах, сверенных до 1e-14. Замена затронет
  все опубликованные числа, поэтому вынесена в план отдельным пунктом.
* Референсная реализация медленная: O(N⁴) без скрининга, один поток, чистый
  Python во внутренних циклах. Это сознательно (ADR-002): сначала корректный
  эталон, потом оптимизация.

## Принципы

1. **Один backend на все интерфейсы** — GUI, CLI, REST и SDK вызывают одни и те
   же доменные сервисы.
2. **Честность вместо имитации** — нереализованный метод недоступен для выбора,
   а не «приблизительно считается».
3. **Сначала корректность, потом скорость** — референс → верификация →
   профилирование → оптимизация → бенчмарк.
4. **Всё, что влияет на результат, — данные** — спецификация сериализуема и
   хешируется в отпечаток расчёта.
5. **Локализация — часть контракта** — в коде только ключи переводов.
